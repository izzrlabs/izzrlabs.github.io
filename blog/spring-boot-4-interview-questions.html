7 Spring Boot 4 interview questions, answered short

November 18, 2026 · 5 min read

Seven questions an interviewer could actually ask about the jump to Spring Boot 4, each with a short answer and the one follow-up that separates a memorized answer from a real one.

What's the minimum Java version for Spring Boot 4, and what would you actually run?

Spring Boot 4 compiles and runs down to Java 17. That's the floor, not a recommendation. Underneath it, Spring Framework 7 and Jakarta EE 11 also accept 17 as their own minimum. In practice I'd run 21 or 25, both long-term-support releases, because those are the versions still getting security patches years out, not because the framework demands it. The Java 21 baseline IZZR Labs picked for its own products is a separate choice from what Spring Boot 4 will technically accept.

What the interviewer is checking: whether you confuse minimum supported with recommended, and whether you can tell a framework constraint apart from a project's own baseline decision.

My imports are com.fasterxml.jackson.*. What breaks?

Jackson 3 moves its group id and most of its packages over to tools.jackson, so a straightforward rename fixes anything under the old core or databind packages. The cut runs along the artifact line, not annotations versus everything else: jackson-annotations doesn't move at all, so things like @JsonProperty and @JsonIgnore stay right where they were, under com.fasterxml.jackson.annotation. The annotations that actually live in jackson-databind — @JsonSerialize, @JsonDeserialize, @JsonNaming, @JsonPOJOBuilder — move with it, to tools.jackson.databind.annotation. The other shift is ObjectMapper giving ground to JsonMapper, built as an immutable object configured through a builder instead of mutated after construction.

What the interviewer is checking: whether you know the split is by artifact — jackson-annotations versus jackson-databind — and not by "annotations versus the rest." Get that wrong and code that compiled yesterday throws import errors today.

My build warns that spring-boot-starter-web is deprecated. What changed?

It's not a stale local repository cache. The starter itself still resolves, it's just deprecated in favor of more specific modules: a dedicated -webmvc starter in place of the old general-purpose web starter, a separate -aspectj starter, a separate -jackson starter, and a security- prefix added to the OAuth2 starters. The old "classic" names still resolve for now, as a bridge while a project migrates, but they're not where the ecosystem is heading.

What the interviewer is checking: that you reach for the dependency rename before you start deleting local repository folders out of frustration.

@MockBean is gone. What replaces it?

@MockitoBean and @MockitoSpyBean, both of which now live in spring-test itself instead of a Spring Boot-specific package. They were already marked deprecated back in version 3.4, so removal in 4.0 shouldn't surprise anyone who read their build warnings. A junior answer stops at the new annotation name. A senior answer adds why the change is actually better: the new annotations run on a general-purpose bean-override SPI that lives in spring-test itself, the same mechanism behind @TestBean, instead of a Spring Boot-specific shortcut. That doesn't dodge the cost of a fresh ApplicationContext — every distinct combination of overridden beans still gets its own entry in the context cache, same as before — but it means the override mechanism works the same way whether or not Spring Boot is even on the classpath.

What the interviewer is checking: whether you understand the design reasoning behind the change, not only the new name to type.

How do you find the properties that moved?

Add spring-boot-properties-migrator as a dependency, start the application, and read the startup log. It reports every deprecated or renamed property it finds, along with the key that replaced it. It's meant to be temporary: once the log goes quiet, the dependency comes back out of the pom.xml.

What the interviewer is checking: whether you treat it as a diagnostic step, not something left wired permanently into a production build.

What's the JUnit story in Boot 4?

Dropping JUnit 4 and its Vintage engine from spring-boot-starter-test isn't a Boot 4 change — that already happened back in Spring Boot 2.4, so a project on 3.x is just as Jupiter-only as one on 4.0. What is new is on the JUnit side itself: Spring Boot 4.0 manages JUnit 6 (6.0.3 as of Boot 4.0.9), and JUnit 6 formally deprecates the Vintage engine, so test discovery reports an INFO-level discovery issue if it still finds a JUnit 4-style test class anywhere on the classpath — that's a note from test discovery, not a warning at application startup. Either way, code still written the old JUnit 4 way needs to migrate before the framework upgrade, not during it.

What the interviewer is checking: this is deliberately the riskiest line in the whole list — whether you separate a years-old Spring Boot change from what's actually new in 4.0, and whether you can name the actual JUnit version Boot 4 ships instead of waving at "the current generation."

Walk me through the upgrade order on a real service.

Clear out every deprecation warning while the service is still on the previous feature release, since that version tells you what's coming without breaking anything yet. Then raise the Java version, add the properties migrator along with the classic starter names as a temporary bridge, and move to Jackson 3 and the new mock annotations one change at a time. Only once all of that has landed and proven itself do I swap the bridge starters for the modular ones and drop the migrator for good. Each of those steps is its own pull request, with a green suite at the end of it — never one pull request that changes everything at once.

What the interviewer is checking: whether your default is a single big-bang pull request, or an order that keeps the service shippable after every single step.
