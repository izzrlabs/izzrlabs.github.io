Your computeIfAbsent cache will crash on recursion (HashMap and ConcurrentHashMap)

November 19, 2026 · 5 min read

Memoizing a recursive function with computeIfAbsent looks like a one-liner. On a HashMap it throws ConcurrentModificationException. On a ConcurrentHashMap it throws IllegalStateException: Recursive update. The fix is three steps: get, compute outside the map, then putIfAbsent.

Everything below runs as one file, RecursiveMemo.java, with java RecursiveMemo.java (no Maven). The output shown is from Java 17 (same on 21).

The innocent version

Fibonacci with a cache. The recursion lives inside the mapping function:

static long brokenFib(Map<Integer, Long> cache, int n) {
    if (n < 2) return n;
    return cache.computeIfAbsent(n,
            k -> brokenFib(cache, k - 1) + brokenFib(cache, k - 2));
}

It reads well, and it looks like exactly what computeIfAbsent is for: "get the value, or compute and store it."

What happens when you run it

I called brokenFib(map, 30) on each map type:

HashMap: java.util.ConcurrentModificationException
ConcurrentHashMap: java.lang.IllegalStateException: Recursive update

Same code, two maps, two different exceptions, and neither message tells you what you did wrong.

Why it fails

The Map.computeIfAbsent javadoc says it plainly: the mapping function should not modify this map during computation. A recursive call that fills the cache does exactly that. The two maps just notice it in different ways.

HashMap. Since Java 9, HashMap.computeIfAbsent remembers its internal modCount before it calls your function. When the function returns, it compares the two numbers. Your recursive calls inserted entries, so the count changed, and the map throws ConcurrentModificationException. Java 8 did not check, so the same code could silently corrupt the table. The new exception is the better outcome.

ConcurrentHashMap. When the key's bin is empty, computeIfAbsent parks a placeholder (a ReservationNode) in it and holds that bin while your function runs. If your function lands back on a bin that is already reserved, the map sees a recursive update and throws. In Java 8 the same code could loop forever instead of failing fast.

One caveat: the CHM check is best-effort. It fires when the recursion hits a bin that is reserved or locked by a call further up the stack. A recursive function whose keys land in other bins can get through on some inputs and fail on others. That makes it worse, not safer. The javadoc says don't, so don't.

The fix

Do the lookup and the computation outside the map, and use the map only to store:

static long fib(Map<Integer, Long> cache, int n) {
    if (n < 2) return n;
    Long hit = cache.get(n);
    if (hit != null) return hit;
    long value = fib(cache, n - 1) + fib(cache, n - 2);
    Long raced = cache.putIfAbsent(n, value);
    return raced != null ? raced : value;
}

putIfAbsent returns the existing value if another thread got there first, so on a ConcurrentHashMap every caller still ends up with the same answer. Output for both map types:

HashMap fib(90)             = 2880067194370816120
ConcurrentHashMap fib(90)   = 2880067194370816120
iterative fib(90)           = 2880067194370816120

The third line is the loop version, which needs no map at all. For Fibonacci specifically, the loop is the better answer. The get / compute / putIfAbsent pattern is for cases where the recursion is real, such as a tree or a dependency graph.

The trade-off: with this pattern two threads can compute the same key at the same time, and one result is thrown away. For pure functions that is harmless. If the computation is expensive or has side effects, you need something else (see the next section).

What computeIfAbsent actually guarantees

Don't throw the method away. On ConcurrentHashMap, the function runs at most once per absent key, even when threads race. I tested it with two threads released together by a CountDownLatch, both asking for the same key, with an AtomicInteger counting calls:

function calls = 1, value = loaded

The second thread blocks on the bin until the first finishes, then reads the stored value. That makes computeIfAbsent the right tool for "load this expensive thing once": reading a config file, opening a connection, building a parser. Keep it as short as you can: other writers to that bin wait while it runs, and it must not touch the map.

Short version:

  • Function calls other code that never touches the map: use computeIfAbsent.
  • Function recurses through the same map: use get, compute, putIfAbsent, or a loop.

Where this shows up in interviews

"What happens if two threads call computeIfAbsent on the same key?" is a classic Java interview question, and the recursive version is the follow-up that separates people who have read the javadoc from people who have only used the method.
