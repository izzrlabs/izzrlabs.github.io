Stop Claude Code from finishing with a red build

November 18, 2026 · 5 min read

The problem

Claude Code finishes a turn, tells you the feature is done, and the build is red. Nothing in that turn checked it. You find out one of two ways: a few minutes later when CI fails on the pull request, or twenty minutes later when you run the test suite yourself before you push, out of habit, not because Claude asked you to.

It's not that Claude is careless. It edited files, maybe ran one test it picked on its own, decided the task looked finished, and handed control back to you. Nothing in that loop required the whole suite to pass before the turn could end. A hook can require it instead.

Why not on PostToolUse

A build hook wired to PostToolUse runs after every single edit: every method you add, every import you fix, every typo you correct. On a real codebase that means running a Maven build dozens of times during one refactor, most of them on code that isn't finished yet and isn't supposed to compile cleanly mid-edit. That's slow, and it tells you nothing you didn't already expect.

The event you want is Stop. It fires once at the end of a turn, when Claude finishes responding on its own — after every edit for that turn is already done, not after each one on its own. Two edge cases to know: it doesn't fire if the user interrupts instead of Claude finishing by itself, and it fires again, with stop_hook_active set, if an earlier Stop hook already blocked once this same turn — the script below depends on exactly that second case.

Where it goes in settings.json

{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "\"${CLAUDE_PROJECT_DIR}\"/.claude/hooks/require-green-build.sh",
            "timeout": 300
          }
        ]
      }
    ]
  }
}

Two details are worth calling out. The double quotes around ${CLAUDE_PROJECT_DIR} matter: without them, a project directory with a space in its path breaks the command before the hook ever runs. And Stop takes no matcher at all. Unlike PreToolUse or PostToolUse, which filter by tool name, Stop fires on every turn, full stop, with nothing to narrow it down.

The hook, in full

Here's the full script, copy-paste ready. It checks for a build marker, reads whether the current Stop event is already a repeat of a blocked one, runs the build, and either lets the turn end or blocks it with the log attached.

#!/bin/bash
# Stop hook (see settings.json; the Stop event takes no matcher -- it fires once per
# turn, right before Claude is about to hand control back to you).
#
# The problem this avoids: a build hook on PostToolUse re-runs the build after every
# single file edit, which is slow and useless in the middle of a refactor. This script
# runs on Stop instead -- once per turn -- and only when the PostToolUse companion hook
# (format-on-edit.sh) has already marked something build-relevant as changed. Edit only
# a .md file during the turn, and that marker never gets created, so the turn ends with
# no build at all. That's the point, not a bug.
#
# BUILD_CMD: the default below is the fast loop (`mvn -q test`). In a multi-module repo,
# scope it to the module you're actually working in, for example:
#   BUILD_CMD="mvn -q test -pl your-module -am"
# `-pl your-module` tells Maven to build only that module; `-am` ("also make") builds
# whatever that module depends on first, so the scoped build still has everything it
# needs to compile and run.
# A Gradle project would use `gradle check` here instead -- cited as the equivalent,
# not tested: the project this hook was written against is Maven.
set -euo pipefail

BUILD_CMD="mvn -q test"
MAX_CONSECUTIVE_FAILURES=3

PROJECT_DIR="${CLAUDE_PROJECT_DIR:-$PWD}"
MARKER="$PROJECT_DIR/.claude/.build-pending"

if [ ! -f "$MARKER" ]; then
  exit 0  # nothing build-relevant changed this turn -- nothing to prove, let Claude stop
fi

INPUT="$(cat)"
STOP_HOOK_ACTIVE="$(python3 - "$INPUT" <<'PYEOF'
import json, sys
try:
    payload = json.loads(sys.argv[1])
except (IndexError, ValueError):
    print("false")
    sys.exit(0)
print(str(payload.get("stop_hook_active", False)).lower())
PYEOF
)"

FAILURES="$(cat "$MARKER" 2>/dev/null || echo 0)"
case "$FAILURES" in ''|*[!0-9]*) FAILURES=0 ;; esac

if [ "$FAILURES" -ge "$MAX_CONSECUTIVE_FAILURES" ]; then
  echo "require-green-build.sh: build still red after $FAILURES attempts in a row," \
       "giving up instead of looping forever (stop_hook_active=$STOP_HOOK_ACTIVE)." >&2
  rm -f "$MARKER"
  exit 0  # let Claude stop anyway -- a human needs to look at this, not another retry
fi

cd "$PROJECT_DIR"
BUILD_LOG="$(mktemp)"
if $BUILD_CMD >"$BUILD_LOG" 2>&1; then
  rm -f "$MARKER" "$BUILD_LOG"
  exit 0  # green: the marker is cleared, Claude may stop
fi

FAILURES=$((FAILURES + 1))
echo "$FAILURES" > "$MARKER"

{
  echo "require-green-build.sh: \`$BUILD_CMD\` failed (attempt $FAILURES of $MAX_CONSECUTIVE_FAILURES, stop_hook_active=$STOP_HOOK_ACTIVE). Last 20 lines:"
  tail -n 20 "$BUILD_LOG"
} >&2
rm -f "$BUILD_LOG"
exit 2  # blocks the Stop: Claude sees this stderr and keeps working instead of stopping

What a red build looks like

When the build fails, the script exits 2 and writes its message to stderr. Claude Code treats that combination as a block: the turn doesn't end, and Claude sees the stderr text as part of what it reads next, log included. Exit 0 does the opposite — either nothing needed building, or the build came back green, and the turn is free to end as normal.

MAX_CONSECUTIVE_FAILURES set to 3 exists so a genuinely broken build doesn't trap Claude in a retry loop forever. After the third failed build in a row, the next Stop event gives up without running the build again, on the idea that a human should look at it instead of a fourth automatic attempt. stop_hook_active, read out of the JSON Claude Code sends on standard input, tells the script whether this particular Stop event is already the result of an earlier block. It only shapes the message here, not the decision to run the build.

What you'll actually see on a failed attempt is one line on stderr, followed by whatever sits at the tail of the build log:

require-green-build.sh: `mvn -q test` failed (attempt 1 of 3, stop_hook_active=false). Last 20 lines:

— followed, in your own terminal, by the real last 20 lines of that failed mvn -q test run. That part isn't reproduced here, since what shows up depends entirely on your own broken test, not on this script.

The gotcha that makes this hook worth installing

Install only this one script, and you get a hook that stays silent forever. It only runs the build if a marker file, .claude/.build-pending, already exists, and nothing inside this script ever creates that marker. That job belongs to a companion PostToolUse hook, which watches every file Claude edits and creates the marker when the file is one that can actually turn a build red: a .java source file, any pom.xml, a Flyway .sql migration, or an application*.{yml,yaml,properties} config file. One detail matters here: that companion hook only creates the marker if it doesn't already exist ([ -f "$MARKER" ] || echo 0 > "$MARKER") — it never overwrites one that's already there. Write your own version with a plain touch or an unconditional echo > "$MARKER" on every matching edit, and you reset the failure count back to zero each time, so the 3-strikes guard above never gets a chance to fire and a truly broken build blocks forever instead of giving up after three tries.

That split is deliberate, not an accident. A session where Claude only touched a README or a design document never creates the marker, so the Stop hook exits on its very first check and the turn ends with no build at all — instantly, with no multi-minute test tax for a typo fix in a Markdown file. That's the entire point of the marker, not a gap waiting to be patched later.

Limitations

  • Time. A slow suite can blow past the 5-minute timeout set on the hook. Scope the command to the module you're touching with the Maven flags shown above, or swap in a faster BUILD_CMD entirely.
  • Monorepo. This is one command tied to one CLAUDE_PROJECT_DIR, not something that walks every module in a repository one by one looking for the one that changed.
  • Gradle. A Gradle project would use gradle check here instead — cited as the equivalent, not tested, because the project this hook was written against runs on Maven.
  • Requirements. The script needs bash and python3 on the machine running Claude Code. On Windows that means WSL or Git Bash, not a native command prompt.
