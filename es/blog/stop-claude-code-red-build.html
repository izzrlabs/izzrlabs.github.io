Evita que Claude Code termine con el build en rojo

18 de noviembre de 2026 · 5 min de lectura

El problema

Claude Code termina un turno, te dice que la funcionalidad está lista, y el build está en rojo. Nada en ese turno lo comprobó. Te enteras de una de dos formas: unos minutos después, cuando el CI falla en el pull request, o veinte minutos después, cuando tú mismo ejecutas la suite de tests antes del push, por costumbre, no porque Claude te lo pidiera.

No es que Claude sea descuidado. Editó archivos, quizá ejecutó un test que eligió por su cuenta, decidió que la tarea parecía terminada y te devolvió el control. Nada en ese ciclo exigía que toda la suite pasara antes de que el turno pudiera terminar. Un hook puede exigirlo.

Por qué no en PostToolUse

Un hook de build conectado a PostToolUse corre después de cada edición: cada método que añades, cada import que corriges, cada errata que arreglas. En un proyecto real eso significa ejecutar un build de Maven decenas de veces durante una refactorización, la mayoría sobre código que aún no está terminado y que ni debería compilar limpio a mitad de la edición. Es lento, y no te dice nada que no esperaras ya.

El evento que quieres es Stop. Se dispara una vez al final del turno, cuando Claude termina de responder por su cuenta — después de que todas las ediciones de ese turno ya están hechas, no después de cada una. Dos casos límite que conviene saber: no se dispara si el usuario interrumpe en vez de que Claude termine solo, y se dispara de nuevo, con stop_hook_active activado, si un hook de Stop anterior ya bloqueó una vez en este mismo turno — el script de abajo depende justo de ese segundo caso.

Dónde va en settings.json

{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "\"${CLAUDE_PROJECT_DIR}\"/.claude/hooks/require-green-build.sh",
            "timeout": 300
          }
        ]
      }
    ]
  }
}

Dos detalles merecen atención. Las comillas alrededor de ${CLAUDE_PROJECT_DIR} importan: sin ellas, una carpeta de proyecto con un espacio en la ruta rompe el comando antes de que el hook llegue a correr. Y Stop no acepta ningún matcher. A diferencia de PreToolUse o PostToolUse, que filtran por nombre de herramienta, Stop se dispara en cada turno, sin más, sin nada que lo acote.

El hook, completo

Este es el script completo, listo para copiar y pegar. Busca un marcador de build, lee si el evento Stop actual ya es la repetición de uno bloqueado, ejecuta el build y o deja que el turno termine o lo bloquea con el log adjunto.

#!/bin/bash
# Stop hook (see settings.json; the Stop event takes no matcher -- it fires once per
# turn, right before Claude is about to hand control back to you).
#
# The problem this avoids: a build hook on PostToolUse re-runs the build after every
# single file edit, which is slow and useless in the middle of a refactor. This script
# runs on Stop instead -- once per turn -- and only when the PostToolUse companion hook
# (format-on-edit.sh) has already marked something build-relevant as changed. Edit only
# a .md file during the turn, and that marker never gets created, so the turn ends with
# no build at all. That's the point, not a bug.
#
# BUILD_CMD: the default below is the fast loop (`mvn -q test`). In a multi-module repo,
# scope it to the module you're actually working in, for example:
#   BUILD_CMD="mvn -q test -pl your-module -am"
# `-pl your-module` tells Maven to build only that module; `-am` ("also make") builds
# whatever that module depends on first, so the scoped build still has everything it
# needs to compile and run.
# A Gradle project would use `gradle check` here instead -- cited as the equivalent,
# not tested: the project this hook was written against is Maven.
set -euo pipefail

BUILD_CMD="mvn -q test"
MAX_CONSECUTIVE_FAILURES=3

PROJECT_DIR="${CLAUDE_PROJECT_DIR:-$PWD}"
MARKER="$PROJECT_DIR/.claude/.build-pending"

if [ ! -f "$MARKER" ]; then
  exit 0  # nothing build-relevant changed this turn -- nothing to prove, let Claude stop
fi

INPUT="$(cat)"
STOP_HOOK_ACTIVE="$(python3 - "$INPUT" <<'PYEOF'
import json, sys
try:
    payload = json.loads(sys.argv[1])
except (IndexError, ValueError):
    print("false")
    sys.exit(0)
print(str(payload.get("stop_hook_active", False)).lower())
PYEOF
)"

FAILURES="$(cat "$MARKER" 2>/dev/null || echo 0)"
case "$FAILURES" in ''|*[!0-9]*) FAILURES=0 ;; esac

if [ "$FAILURES" -ge "$MAX_CONSECUTIVE_FAILURES" ]; then
  echo "require-green-build.sh: build still red after $FAILURES attempts in a row," \
       "giving up instead of looping forever (stop_hook_active=$STOP_HOOK_ACTIVE)." >&2
  rm -f "$MARKER"
  exit 0  # let Claude stop anyway -- a human needs to look at this, not another retry
fi

cd "$PROJECT_DIR"
BUILD_LOG="$(mktemp)"
if $BUILD_CMD >"$BUILD_LOG" 2>&1; then
  rm -f "$MARKER" "$BUILD_LOG"
  exit 0  # green: the marker is cleared, Claude may stop
fi

FAILURES=$((FAILURES + 1))
echo "$FAILURES" > "$MARKER"

{
  echo "require-green-build.sh: \`$BUILD_CMD\` failed (attempt $FAILURES of $MAX_CONSECUTIVE_FAILURES, stop_hook_active=$STOP_HOOK_ACTIVE). Last 20 lines:"
  tail -n 20 "$BUILD_LOG"
} >&2
rm -f "$BUILD_LOG"
exit 2  # blocks the Stop: Claude sees this stderr and keeps working instead of stopping

Cómo se ve un build en rojo

Cuando el build falla, el script sale con código 2 y escribe su mensaje en stderr. Claude Code trata esa combinación como un bloqueo: el turno no termina, y Claude ve el texto de stderr como parte de lo que lee a continuación, con el log incluido. El código 0 hace lo contrario — o no había nada que compilar, o el build volvió en verde, y el turno puede terminar con normalidad.

MAX_CONSECUTIVE_FAILURES en 3 existe para que un build roto de verdad no atrape a Claude en un ciclo de reintentos para siempre. Tras el tercer fallo seguido, el siguiente evento Stop se rinde sin volver a ejecutar el build, con la idea de que una persona debe mirarlo, no un cuarto intento automático. stop_hook_active, leído del JSON que Claude Code envía por la entrada estándar, le dice al script si este evento Stop ya es resultado de un bloqueo anterior. Aquí solo cambia el mensaje, no la decisión de ejecutar el build.

Lo que verás realmente en un intento fallido es una línea en stderr, seguida de lo que haya al final del log del build:

require-green-build.sh: `mvn -q test` failed (attempt 1 of 3, stop_hook_active=false). Last 20 lines:

— seguida, en tu propia terminal, de las 20 últimas líneas reales de ese mvn -q test fallido. Esa parte no se reproduce aquí, porque lo que aparece depende por completo de tu test roto, no de este script.

La trampa que hace que este hook valga la pena

Instala solo este script y tendrás un hook que se queda callado para siempre. Solo ejecuta el build si ya existe un archivo marcador, .claude/.build-pending, y nada dentro de este script crea ese marcador. Ese trabajo es de un hook PostToolUse compañero, que observa cada archivo que Claude edita y crea el marcador cuando el archivo es uno que de verdad puede poner el build en rojo: un fuente .java, cualquier pom.xml, una migración .sql de Flyway, o un archivo de configuración application*.{yml,yaml,properties}. Un detalle importa aquí: ese hook compañero solo crea el marcador si aún no existe ([ -f "$MARKER" ] || echo 0 > "$MARKER") — nunca sobrescribe uno que ya está. Escribe tu propia versión con un touch simple o un echo > "$MARKER" incondicional en cada edición y reinicias el contador de fallos cada vez, así que la protección de 3 intentos de arriba nunca llega a saltar y un build roto de verdad bloquea para siempre en vez de rendirse tras tres.

Esa división es intencionada, no un accidente. Una sesión en la que Claude solo tocó un README o un documento de diseño nunca crea el marcador, así que el hook de Stop sale en su primera comprobación y el turno termina sin build alguno — al instante, sin pagar minutos de tests por una errata en un archivo Markdown. Ese es todo el sentido del marcador, no un hueco pendiente de arreglar.

Limitaciones

  • Tiempo. Una suite lenta puede pasarse del timeout de 5 minutos definido en el hook. Limita el comando al módulo que estás tocando con los flags de Maven mostrados arriba, o cambia a un BUILD_CMD más rápido.
  • Monorepo. Es un comando ligado a un CLAUDE_PROJECT_DIR, no algo que recorre cada módulo del repositorio buscando el que cambió.
  • Gradle. Un proyecto Gradle usaría gradle check aquí — citado como equivalente, no probado, porque el proyecto para el que se escribió este hook usa Maven.
  • Requisitos. El script necesita bash y python3 en la máquina que ejecuta Claude Code. En Windows eso significa WSL o Git Bash, no el símbolo del sistema nativo.
