Tu caché con computeIfAbsent va a fallar en la recursión (HashMap y ConcurrentHashMap)

19 de noviembre de 2026 · 5 min de lectura

Memoizar una función recursiva con computeIfAbsent parece cosa de una línea. En un HashMap lanza ConcurrentModificationException. En un ConcurrentHashMap lanza IllegalStateException: Recursive update. La corrección tiene tres pasos: get, calcular fuera del map y luego putIfAbsent.

Todo lo de abajo corre en un solo archivo, RecursiveMemo.java, con java RecursiveMemo.java (sin Maven). La salida que se muestra es de Java 17 (igual en 21).

La versión inocente

Fibonacci con caché. La recursión vive dentro de la función de mapeo:

static long brokenFib(Map<Integer, Long> cache, int n) {
    if (n < 2) return n;
    return cache.computeIfAbsent(n,
            k -> brokenFib(cache, k - 1) + brokenFib(cache, k - 2));
}

Se lee bien, y parece justo para lo que existe computeIfAbsent: "obtén el valor, o calcúlalo y guárdalo".

Qué pasa cuando lo ejecutas

Llamé a brokenFib(map, 30) con cada tipo de map:

HashMap: java.util.ConcurrentModificationException
ConcurrentHashMap: java.lang.IllegalStateException: Recursive update

Mismo código, dos maps, dos excepciones distintas, y ningún mensaje te dice qué hiciste mal.

Por qué falla

El javadoc de Map.computeIfAbsent lo dice claramente: la función de mapeo no debe modificar este map durante el cálculo. Una llamada recursiva que llena la caché hace exactamente eso. Los dos maps solo lo detectan de formas distintas.

HashMap. Desde Java 9, HashMap.computeIfAbsent guarda su modCount interno antes de llamar a tu función. Cuando la función vuelve, compara los dos números. Tus llamadas recursivas insertaron entradas, el contador cambió, y el map lanza ConcurrentModificationException. Java 8 no lo comprobaba, así que el mismo código podía corromper la tabla en silencio. La excepción nueva es el mejor resultado.

ConcurrentHashMap. Cuando el bin de la clave está vacío, computeIfAbsent deja en él un marcador (un ReservationNode) y retiene ese bin mientras corre tu función. Si tu función vuelve a caer en un bin que ya está reservado, el map detecta una actualización recursiva y lanza la excepción. En Java 8, el mismo código podía quedarse en un bucle infinito en vez de fallar rápido.

Un matiz: la comprobación de CHM es de mejor esfuerzo. Salta cuando la recursión llega a un bin reservado o bloqueado por una llamada más arriba en la pila. Una función recursiva cuyas claves caen en otros bins puede pasar con algunas entradas y fallar con otras. Eso lo hace peor, no más seguro. El javadoc dice que no, así que no.

La corrección

Haz la búsqueda y el cálculo fuera del map, y usa el map solo para guardar:

static long fib(Map<Integer, Long> cache, int n) {
    if (n < 2) return n;
    Long hit = cache.get(n);
    if (hit != null) return hit;
    long value = fib(cache, n - 1) + fib(cache, n - 2);
    Long raced = cache.putIfAbsent(n, value);
    return raced != null ? raced : value;
}

putIfAbsent devuelve el valor existente si otro hilo llegó primero, así que en un ConcurrentHashMap todos los que llaman siguen recibiendo la misma respuesta. Salida para los dos tipos de map:

HashMap fib(90)             = 2880067194370816120
ConcurrentHashMap fib(90)   = 2880067194370816120
iterative fib(90)           = 2880067194370816120

La tercera línea es la versión con bucle, que no necesita map. Para Fibonacci en concreto, el bucle es la mejor respuesta. El patrón get / calcular / putIfAbsent es para casos en los que la recursión es real, como un árbol o un grafo de dependencias.

El costo: con este patrón, dos hilos pueden calcular la misma clave a la vez, y uno de los resultados se descarta. Para funciones puras eso no hace daño. Si el cálculo es caro o tiene efectos secundarios, necesitas otra cosa (ver la siguiente sección).

Lo que computeIfAbsent garantiza de verdad

No tires el método. En ConcurrentHashMap, la función corre como mucho una vez por clave ausente, incluso cuando los hilos compiten. Lo probé con dos hilos liberados a la vez por un CountDownLatch, los dos pidiendo la misma clave, con un AtomicInteger contando las llamadas:

function calls = 1, value = loaded

El segundo hilo se bloquea en el bin hasta que el primero termina y luego lee el valor guardado. Eso hace de computeIfAbsent la herramienta correcta para "cargar esta cosa cara una sola vez": leer un archivo de configuración, abrir una conexión, construir un parser. Mantén la función lo más corta posible: otras escrituras en ese bin esperan mientras corre, y no debe tocar el map.

En resumen:

  • La función llama a otro código que nunca toca el map: usa computeIfAbsent.
  • La función hace recursión sobre el mismo map: usa get, calcula, putIfAbsent, o un bucle.

Dónde aparece esto en entrevistas

"¿Qué pasa si dos hilos llaman a computeIfAbsent con la misma clave?" es una pregunta clásica de entrevista de Java, y la versión recursiva es la repregunta que separa a quien leyó el javadoc de quien solo usó el método.
