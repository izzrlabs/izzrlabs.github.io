Seu cache com computeIfAbsent vai quebrar na recursão (HashMap e ConcurrentHashMap)

19 de novembro de 2026 · 5 min de leitura

Memoizar uma função recursiva com computeIfAbsent parece coisa de uma linha. Num HashMap, lança ConcurrentModificationException. Num ConcurrentHashMap, lança IllegalStateException: Recursive update. A correção tem três passos: get, calcular fora do map e depois putIfAbsent.

Tudo abaixo roda num arquivo só, RecursiveMemo.java, com java RecursiveMemo.java (sem Maven). A saída mostrada é do Java 17 (igual no 21).

A versão inocente

Fibonacci com cache. A recursão fica dentro da função de mapeamento:

static long brokenFib(Map<Integer, Long> cache, int n) {
    if (n < 2) return n;
    return cache.computeIfAbsent(n,
            k -> brokenFib(cache, k - 1) + brokenFib(cache, k - 2));
}

Lê bem, e parece exatamente o que o computeIfAbsent promete: "pega o valor, ou calcula e guarda".

O que acontece quando você roda

Chamei brokenFib(map, 30) em cada tipo de map:

HashMap: java.util.ConcurrentModificationException
ConcurrentHashMap: java.lang.IllegalStateException: Recursive update

Mesmo código, dois maps, duas exceções diferentes, e nenhuma das mensagens diz o que você fez de errado.

Por que falha

O javadoc de Map.computeIfAbsent diz com todas as letras: a função de mapeamento não deve modificar este map durante o cálculo. Uma chamada recursiva que preenche o cache faz exatamente isso. Os dois maps só percebem de jeitos diferentes.

HashMap. Desde o Java 9, o HashMap.computeIfAbsent guarda o seu modCount interno antes de chamar a sua função. Quando a função retorna, ele compara os dois números. As suas chamadas recursivas inseriram entradas, o contador mudou, e o map lança ConcurrentModificationException. O Java 8 não conferia, então o mesmo código podia corromper a tabela em silêncio. A exceção nova é o resultado melhor.

ConcurrentHashMap. Quando o bin da chave está vazio, o computeIfAbsent coloca nele um marcador (um ReservationNode) e segura esse bin enquanto a sua função roda. Se a sua função cai de volta num bin que já está reservado, o map percebe uma atualização recursiva e lança a exceção. No Java 8, o mesmo código podia ficar em loop para sempre em vez de falhar rápido.

Um porém: a checagem do CHM é de melhor esforço. Ela dispara quando a recursão bate num bin reservado ou travado por uma chamada mais acima na pilha. Uma função recursiva cujas chaves caem em outros bins pode passar com algumas entradas e falhar com outras. Isso deixa pior, não mais seguro. O javadoc diz para não fazer, então não faça.

A correção

Faça a busca e o cálculo fora do map, e use o map só para guardar:

static long fib(Map<Integer, Long> cache, int n) {
    if (n < 2) return n;
    Long hit = cache.get(n);
    if (hit != null) return hit;
    long value = fib(cache, n - 1) + fib(cache, n - 2);
    Long raced = cache.putIfAbsent(n, value);
    return raced != null ? raced : value;
}

O putIfAbsent devolve o valor que já existe se outra thread chegou antes, então num ConcurrentHashMap todo mundo que chama ainda recebe a mesma resposta. Saída para os dois tipos de map:

HashMap fib(90)             = 2880067194370816120
ConcurrentHashMap fib(90)   = 2880067194370816120
iterative fib(90)           = 2880067194370816120

A terceira linha é a versão com loop, que nem precisa de map. Para Fibonacci, especificamente, o loop é a resposta melhor. O padrão get / calcular / putIfAbsent é para casos em que a recursão é de verdade, como uma árvore ou um grafo de dependências.

O custo: com esse padrão, duas threads podem calcular a mesma chave ao mesmo tempo, e um dos resultados vai fora. Para funções puras, isso não faz mal. Se o cálculo é caro ou tem efeitos colaterais, você precisa de outra coisa (veja a próxima seção).

O que o computeIfAbsent garante de verdade

Não jogue o método fora. No ConcurrentHashMap, a função roda no máximo uma vez por chave ausente, mesmo quando threads disputam. Testei com duas threads liberadas juntas por um CountDownLatch, as duas pedindo a mesma chave, com um AtomicInteger contando as chamadas:

function calls = 1, value = loaded

A segunda thread fica bloqueada no bin até a primeira terminar e depois lê o valor guardado. Isso faz do computeIfAbsent a ferramenta certa para "carregar essa coisa cara uma vez só": ler um arquivo de configuração, abrir uma conexão, montar um parser. Deixe a função o mais curta possível: outras escritas naquele bin esperam enquanto ela roda, e ela não pode mexer no map.

Resumindo:

  • A função chama outro código que nunca mexe no map: use computeIfAbsent.
  • A função faz recursão pelo mesmo map: use get, calcule, putIfAbsent, ou um loop.

Onde isso aparece em entrevista
