7 perguntas de entrevista sobre Spring Boot 4, com respostas curtas

18 de novembro de 2026 · 5 min de leitura

Sete perguntas que um entrevistador pode mesmo fazer sobre o salto para o Spring Boot 4, cada uma com uma resposta curta e a pergunta seguinte que separa uma resposta decorada de uma de verdade.

Qual é a versão mínima do Java para o Spring Boot 4, e qual você usaria de fato?

O Spring Boot 4 compila e roda a partir do Java 17. Esse é o piso, não uma recomendação. Por baixo, o Spring Framework 7 e o Jakarta EE 11 também aceitam o 17 como mínimo. Na prática, eu rodaria o 21 ou o 25, as duas versões de suporte longo, porque são elas que ainda recebem correções de segurança daqui a anos, não porque o framework exige. A base de Java 21 que a IZZR Labs escolheu para os seus produtos é uma escolha separada do que o Spring Boot 4 aceita tecnicamente.

O que o entrevistador está conferindo: se você confunde mínimo suportado com recomendado, e se sabe separar uma restrição do framework de uma decisão de base do próprio projeto.

Meus imports são com.fasterxml.jackson.*. O que quebra?

O Jackson 3 muda o group id e a maioria dos pacotes para tools.jackson, então uma troca de nome direta resolve tudo o que estava nos pacotes antigos de core ou databind. O corte segue o artefato, não a divisão entre anotações e o resto: o jackson-annotations não muda nada, então coisas como @JsonProperty e @JsonIgnore continuam onde estavam, em com.fasterxml.jackson.annotation. As anotações que moram de fato no jackson-databind — @JsonSerialize, @JsonDeserialize, @JsonNaming, @JsonPOJOBuilder — vão junto com ele, para tools.jackson.databind.annotation. A outra mudança é o ObjectMapper perdendo espaço para o JsonMapper, montado como um objeto imutável configurado por um builder em vez de alterado depois de criado.

O que o entrevistador está conferindo: se você sabe que a divisão é por artefato — jackson-annotations contra jackson-databind — e não por "anotações contra o resto". Errar isso faz um código que compilava ontem dar erro de import hoje.

Meu build avisa que o spring-boot-starter-web está deprecated. O que mudou?

Não é cache velho do repositório local. O starter ainda resolve, só está deprecated em favor de módulos mais específicos: um starter -webmvc dedicado no lugar do antigo starter web genérico, um starter -aspectj separado, um starter -jackson separado, e o prefixo security- nos starters de OAuth2. Os nomes "clássicos" antigos ainda resolvem por enquanto, como ponte enquanto o projeto migra, mas não é para lá que o ecossistema está indo.

O que o entrevistador está conferindo: se você vai direto na troca de nome da dependência antes de sair apagando pastas do repositório local de raiva.

O @MockBean sumiu. O que entra no lugar?

@MockitoBean e @MockitoSpyBean, que agora moram no próprio spring-test em vez de num pacote específico do Spring Boot. Elas já estavam marcadas como deprecated desde a versão 3.4, então a remoção no 4.0 não deveria surpreender quem leu os avisos do build. Uma resposta júnior para no nome da anotação nova. Uma resposta sênior acrescenta por que a mudança é melhor: as anotações novas rodam sobre uma SPI genérica de sobrescrita de beans que mora no próprio spring-test, o mesmo mecanismo por trás do @TestBean, em vez de um atalho específico do Spring Boot. Isso não evita o custo de um ApplicationContext novo — cada combinação diferente de beans sobrescritos ainda ganha a sua própria entrada no cache de contextos, como antes — mas faz o mecanismo de sobrescrita funcionar do mesmo jeito com ou sem o Spring Boot no classpath.

O que o entrevistador está conferindo: se você entende o raciocínio de design por trás da mudança, não só o nome novo para digitar.

Como você acha as propriedades que mudaram?

Adicione o spring-boot-properties-migrator como dependência, suba a aplicação e leia o log de inicialização. Ele relata cada propriedade deprecated ou renomeada que encontra, junto com a chave que a substituiu. É para ser temporário: quando o log fica quieto, a dependência sai do pom.xml.

O que o entrevistador está conferindo: se você trata isso como um passo de diagnóstico, não como algo deixado para sempre num build de produção.

Como fica o JUnit no Boot 4?

Tirar o JUnit 4 e o seu engine Vintage do spring-boot-starter-test não é mudança do Boot 4 — isso já aconteceu no Spring Boot 2.4, então um projeto no 3.x é tão só-Jupiter quanto um no 4.0. O que é novo está do lado do próprio JUnit: o Spring Boot 4.0 gerencia o JUnit 6 (6.0.3 no Boot 4.0.9), e o JUnit 6 marca formalmente o engine Vintage como deprecated, então a descoberta de testes relata um aviso de nível INFO se ainda encontrar uma classe de teste no estilo JUnit 4 em qualquer lugar do classpath — é uma nota da descoberta de testes, não um aviso na inicialização da aplicação. De qualquer forma, código ainda escrito no jeito antigo do JUnit 4 precisa migrar antes da atualização do framework, não durante.

O que o entrevistador está conferindo: esta é de propósito a linha mais arriscada da lista — se você separa uma mudança antiga do Spring Boot do que é novo de verdade no 4.0, e se sabe dizer a versão do JUnit que vem com o Boot 4 em vez de falar vagamente em "a geração atual".

Me explique a ordem da atualização num serviço real.

Limpe todos os avisos de deprecated enquanto o serviço ainda está na versão anterior, porque essa versão te mostra o que vem sem quebrar nada ainda. Depois suba a versão do Java, adicione o migrador de propriedades e os nomes clássicos dos starters como ponte temporária, e passe para o Jackson 3 e as anotações novas de mock uma mudança por vez. Só quando tudo isso já entrou e se provou eu troco os starters de ponte pelos modulares e tiro o migrador de vez. Cada um desses passos é um pull request próprio, com a suíte verde no fim — nunca um pull request que muda tudo de uma vez.

O que o entrevistador está conferindo: se o seu padrão é um pull request gigante de uma vez só, ou uma ordem que mantém o serviço pronto para ir ao ar depois de cada passo.
