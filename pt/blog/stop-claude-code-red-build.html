Impeça o Claude Code de terminar com o build vermelho

18 de novembro de 2026 · 5 min de leitura

O problema

O Claude Code termina um turno, diz que a funcionalidade está pronta, e o build está vermelho. Nada naquele turno conferiu. Você descobre de um de dois jeitos: alguns minutos depois, quando o CI falha no pull request, ou vinte minutos depois, quando você mesmo roda a suíte de testes antes do push, por hábito, não porque o Claude pediu.

Não é que o Claude seja descuidado. Ele editou arquivos, talvez rodou um teste que escolheu sozinho, achou que a tarefa estava pronta e devolveu o controle para você. Nada nesse ciclo exigia que a suíte inteira passasse antes de o turno acabar. Um hook pode exigir.

Por que não no PostToolUse

Um hook de build ligado ao PostToolUse roda depois de cada edição: cada método que você adiciona, cada import que você corrige, cada erro de digitação que você conserta. Num projeto real, isso significa rodar um build do Maven dezenas de vezes durante uma refatoração, a maioria delas em código que ainda não está pronto e nem deveria compilar limpo no meio da edição. É lento, e não te diz nada que você já não esperasse.

O evento que você quer é o Stop. Ele dispara uma vez no fim do turno, quando o Claude termina de responder por conta própria — depois que todas as edições daquele turno já foram feitas, não depois de cada uma. Dois casos de borda para saber: ele não dispara se o usuário interrompe em vez de o Claude terminar sozinho, e dispara de novo, com stop_hook_active ligado, se um hook de Stop anterior já bloqueou uma vez neste mesmo turno — o script abaixo depende justamente desse segundo caso.

Onde ele entra no settings.json

{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "\"${CLAUDE_PROJECT_DIR}\"/.claude/hooks/require-green-build.sh",
            "timeout": 300
          }
        ]
      }
    ]
  }
}

Dois detalhes merecem atenção. As aspas em volta de ${CLAUDE_PROJECT_DIR} importam: sem elas, uma pasta de projeto com espaço no caminho quebra o comando antes de o hook rodar. E o Stop não aceita matcher nenhum. Diferente do PreToolUse ou do PostToolUse, que filtram pelo nome da ferramenta, o Stop dispara em todo turno, ponto, sem nada para restringir.

O hook, completo

Este é o script completo, pronto para copiar e colar. Ele procura um marcador de build, lê se o evento Stop atual já é a repetição de um bloqueado, roda o build e ou deixa o turno acabar ou bloqueia com o log junto.

#!/bin/bash
# Stop hook (see settings.json; the Stop event takes no matcher -- it fires once per
# turn, right before Claude is about to hand control back to you).
#
# The problem this avoids: a build hook on PostToolUse re-runs the build after every
# single file edit, which is slow and useless in the middle of a refactor. This script
# runs on Stop instead -- once per turn -- and only when the PostToolUse companion hook
# (format-on-edit.sh) has already marked something build-relevant as changed. Edit only
# a .md file during the turn, and that marker never gets created, so the turn ends with
# no build at all. That's the point, not a bug.
#
# BUILD_CMD: the default below is the fast loop (`mvn -q test`). In a multi-module repo,
# scope it to the module you're actually working in, for example:
#   BUILD_CMD="mvn -q test -pl your-module -am"
# `-pl your-module` tells Maven to build only that module; `-am` ("also make") builds
# whatever that module depends on first, so the scoped build still has everything it
# needs to compile and run.
# A Gradle project would use `gradle check` here instead -- cited as the equivalent,
# not tested: the project this hook was written against is Maven.
set -euo pipefail

BUILD_CMD="mvn -q test"
MAX_CONSECUTIVE_FAILURES=3

PROJECT_DIR="${CLAUDE_PROJECT_DIR:-$PWD}"
MARKER="$PROJECT_DIR/.claude/.build-pending"

if [ ! -f "$MARKER" ]; then
  exit 0  # nothing build-relevant changed this turn -- nothing to prove, let Claude stop
fi

INPUT="$(cat)"
STOP_HOOK_ACTIVE="$(python3 - "$INPUT" <<'PYEOF'
import json, sys
try:
    payload = json.loads(sys.argv[1])
except (IndexError, ValueError):
    print("false")
    sys.exit(0)
print(str(payload.get("stop_hook_active", False)).lower())
PYEOF
)"

FAILURES="$(cat "$MARKER" 2>/dev/null || echo 0)"
case "$FAILURES" in ''|*[!0-9]*) FAILURES=0 ;; esac

if [ "$FAILURES" -ge "$MAX_CONSECUTIVE_FAILURES" ]; then
  echo "require-green-build.sh: build still red after $FAILURES attempts in a row," \
       "giving up instead of looping forever (stop_hook_active=$STOP_HOOK_ACTIVE)." >&2
  rm -f "$MARKER"
  exit 0  # let Claude stop anyway -- a human needs to look at this, not another retry
fi

cd "$PROJECT_DIR"
BUILD_LOG="$(mktemp)"
if $BUILD_CMD >"$BUILD_LOG" 2>&1; then
  rm -f "$MARKER" "$BUILD_LOG"
  exit 0  # green: the marker is cleared, Claude may stop
fi

FAILURES=$((FAILURES + 1))
echo "$FAILURES" > "$MARKER"

{
  echo "require-green-build.sh: \`$BUILD_CMD\` failed (attempt $FAILURES of $MAX_CONSECUTIVE_FAILURES, stop_hook_active=$STOP_HOOK_ACTIVE). Last 20 lines:"
  tail -n 20 "$BUILD_LOG"
} >&2
rm -f "$BUILD_LOG"
exit 2  # blocks the Stop: Claude sees this stderr and keeps working instead of stopping

Como fica um build vermelho

Quando o build falha, o script sai com código 2 e escreve a mensagem no stderr. O Claude Code trata essa combinação como bloqueio: o turno não acaba, e o Claude vê o texto do stderr como parte do que lê em seguida, com o log junto. O código 0 faz o contrário — ou não havia nada para buildar, ou o build voltou verde, e o turno pode acabar normalmente.

O MAX_CONSECUTIVE_FAILURES em 3 existe para que um build quebrado de verdade não prenda o Claude num ciclo de tentativas para sempre. Depois da terceira falha seguida, o próximo evento Stop desiste sem rodar o build de novo, com a ideia de que uma pessoa deve olhar, e não uma quarta tentativa automática. O stop_hook_active, lido do JSON que o Claude Code manda na entrada padrão, diz ao script se este evento Stop já é resultado de um bloqueio anterior. Aqui ele só muda a mensagem, não a decisão de rodar o build.

O que você vai ver de fato numa tentativa que falhou é uma linha no stderr, seguida do que estiver no fim do log do build:

require-green-build.sh: `mvn -q test` failed (attempt 1 of 3, stop_hook_active=false). Last 20 lines:

— seguida, no seu terminal, das 20 últimas linhas reais daquele mvn -q test que falhou. Essa parte não está reproduzida aqui, porque o que aparece depende inteiramente do seu teste quebrado, não deste script.

A pegadinha que faz este hook valer a pena

Instale só este script e você terá um hook que fica calado para sempre. Ele só roda o build se um arquivo marcador, .claude/.build-pending, já existir, e nada dentro deste script cria esse marcador. Esse trabalho é de um hook PostToolUse companheiro, que observa cada arquivo que o Claude edita e cria o marcador quando o arquivo é um que pode de fato deixar o build vermelho: um fonte .java, qualquer pom.xml, uma migração .sql do Flyway, ou um arquivo de configuração application*.{yml,yaml,properties}. Um detalhe importa aqui: esse hook companheiro só cria o marcador se ele ainda não existe ([ -f "$MARKER" ] || echo 0 > "$MARKER") — ele nunca sobrescreve um que já está lá. Escreva a sua própria versão com um touch simples ou um echo > "$MARKER" incondicional a cada edição e você zera a contagem de falhas toda vez, então a proteção de 3 tentativas acima nunca chega a disparar e um build quebrado de verdade bloqueia para sempre em vez de desistir depois de três.

Essa divisão é de propósito, não por acaso. Uma sessão em que o Claude só mexeu num README ou num documento de design nunca cria o marcador, então o hook de Stop sai logo na primeira checagem e o turno acaba sem build nenhum — na hora, sem pagar minutos de testes por um erro de digitação num arquivo Markdown. Esse é todo o sentido do marcador, não uma falha esperando correção.

Limitações

  • Tempo. Uma suíte lenta pode passar do timeout de 5 minutos definido no hook. Restrinja o comando ao módulo em que você está mexendo com as flags do Maven mostradas acima, ou troque por um BUILD_CMD mais rápido.
  • Monorepo. É um comando ligado a um CLAUDE_PROJECT_DIR, não algo que percorre cada módulo do repositório procurando o que mudou.
  • Gradle. Um projeto Gradle usaria gradle check aqui — citado como equivalente, não testado, porque o projeto para o qual este hook foi escrito usa Maven.
  • Requisitos. O script precisa de bash e python3 na máquina que roda o Claude Code. No Windows, isso significa WSL ou Git Bash, não o prompt de comando nativo.
